# Ephor — Developer Experience Feedback (Arc + Circle)

Candid notes for Circle DevRel, captured while building. Marked **[actual]** (experienced in this build) vs **[anticipated]** (expected at integration; will be confirmed after deployment — see BLOCKERS.md).

## What worked well
- **[actual] USDC-as-gas is a genuinely clarifying mental model.** For a continuity product it is a feature, not a convenience: a successor keeps the company running without ever holding a separate gas token. It made the "capped successor keeps paying payroll" story trivial to reason about.
- **[actual] Block-count windows over timestamps.** Being told up front that Arc timestamps repeat and to use block height pushed us to a *better* design — provable, reorg-resistant succession windows. This should be louder in the docs; it changes how you architect any time-based mechanism.
- **[actual] Standard EVM + Foundry.** `solc 0.8.24` + OpenZeppelin v5 + forge compiled and tested with zero Arc-specific shims. The whole invariant suite runs locally against a mock ERC-20.
- **[actual] arcscan is Blockscout, and `forge verify-contract` just works.** `testnet.arcscan.app` runs Blockscout v11.2.3 with the Rust verifier microservice enabled; `solc 0.8.24` is in its supported list. All three contracts verified on the first try with `forge verify-contract <addr> <path>:<name> --verifier blockscout --verifier-url https://testnet.arcscan.app/api/ --compiler-version 0.8.24 --num-of-optimizations 200 --constructor-args <abi-encoded>`. This resolves the one open acceptance-criterion unknown from the earlier notes — no Etherscan API key needed.

## Friction / requests
- **[actual] EVM version isn't obvious.** We defaulted to `evm_version = "shanghai"` to be safe (PUSH0, no Cancun-only opcodes). A single authoritative line in the docs — "Arc supports EVM version X as of date Y" — would remove a deploy-time unknown. If Cancun (transient storage, MCOPY) is supported, say so; it affects optimizer output.
- **[anticipated] USYC entitlements gating.** The brief flags that `Entitlements` may gate USYC minting via the Teller. A copy-pasteable "here's how to check whether your address is entitled, and what to do if not" snippet would save a day-1 probe. We built a labeled `MockYieldVault` fallback in anticipation.
- **[anticipated] CCTP v2 domain table.** We hard-coded Arc = domain 26 and Base Sepolia = 6 from the brief. A canonical, versioned domain table in the docs (with testnet TokenMessengerV2 addresses per chain) would remove copy errors.
- **[anticipated] App Kit Swap from a headless/Node context.** The Swap leg is described for the browser App Kit; a Node/viem recipe for the same swap (for keepers and scripts) would help backend integrations.
- **[actual] Faucet limits (20/asset/2h/address)** are fine for one demo but tight for seeding a multi-actor demo (operator + 2 successors + vendor + team). A one-shot "fund this set of addresses" faucet mode would speed demo setup.
- **[actual] Entity Secret registration is a one-shot footgun.** For developer-controlled wallets the recovery file downloads **only once**, during `registerEntitySecretCiphertext`, and there is no reset path without it. A failed file-write *after* the network registration has already succeeded leaves the entity registered-but-locked, with no self-serve recovery even on a test account. Two fixes would help: make registration idempotent (or offer a Console-side reset for test entities), and have the SDK persist the recovery material *before* marking the entity registered. We hit exactly this and moved the demo actors to plain EOAs.

- **[actual] `forge script` can't simulate Arc's native token precompiles.** Arc's USDC (`0x3600…`) delegates to an implementation that staticcalls a native blocklist precompile at `0x1800…0001`. In forge's local/forked EVM that precompile isn't executable, so any `forge script` touching `transferFrom`/`approve` reverts in simulation with `StackUnderflow` *before* it can broadcast — even with a valid fork URL. We deployed fine via `forge script` (no token transfers) but had to seed the vault with `cast send` (and the keeper uses viem), which run on the real node where the precompile exists. A documented list of Arc's native precompiles (addresses + how to fork or `vm.etch`-mock them for foundry/hardhat) would save integrators a confusing debug loop.
- **[actual] Empty `[etherscan].url` breaks `--broadcast`.** With an `[etherscan]` entry whose `url` resolves to an empty string, `forge script --broadcast` fails with `relative URL without a base` even without `--verify`. Non-obvious; a clearer error ("etherscan url empty for chain X") would help. We kept the block disabled and verified out-of-band with explicit `--verifier blockscout --verifier-url` flags (see above), which sidesteps this entirely.
- **[actual] `eth_getLogs` is capped at a 10,000-block range.** The public RPC rejects wider ranges with `-32614 "eth_getLogs is limited to a 10,000 range"`. At ~0.5s/block that's ~85 min of history per call, so any historical indexer must page backward in 10k chunks (and blocks accrue fast — ~130k in a day). Our live dashboard's activity feed reads a single recent 9k-block window, which is exactly right for a live-driven demo but means an events UI needs a keeper-backed index for deep history. A documented per-method limits table (getLogs range, batch size, rate caps) would help sizing.

## Suggestions
- Publish a minimal **Foundry `foundry.toml` for Arc** (rpc endpoint, verifier config, recommended `evm_version`) as a starter — we reverse-engineered ours.
- Put the **Blockscout verify recipe** in the docs (`--verifier blockscout --verifier-url https://testnet.arcscan.app/api/`). It works today but is undocumented — we found it by fingerprinting the explorer. (Resolves the earlier "biggest unknown"; the acceptance criterion "deployed **and verified**" is now met.)
- Publish a **per-method RPC limits table** (getLogs 10k-block range, batch size, rate caps) so integrators can size indexers correctly.
